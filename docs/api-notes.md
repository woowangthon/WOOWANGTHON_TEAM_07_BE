# 공공데이터 API 확인 결과

> 상태: 실제 응답으로 확인한 항목과 미확인 항목을 구분한다. 미확인 항목은 `(미검증)`으로 표시한다.
> 키는 이 문서와 샘플에 포함하지 않는다.

## OA-15994 승강기 가동현황 (Issue #9)

### 1. 호출 방식
- 엔드포인트: `http://openapi.seoul.go.kr:8088/{KEY}/json/SeoulMetroFaciInfo/{시작}/{끝}/`
- 서비스명 `SeoulMetroFaciInfo`는 호출로 확인했다. 이름은 로컬 CSV 파일명과 같다.
- 한 번에 최대 1,000건을 받는다. 전체 2,809건을 3번 호출해서 모두 받았다(결과 코드 3회 모두 `INFO-000`).
- 샘플: `docs/samples/OA-15994_SeoulMetroFaciInfo_2026-11-13.json` (전체 2,809건, 키 없음)

### 2. 응답 구조
- 최상위 키: `SeoulMetroFaciInfo`
- 하위 키: `list_total_count`(전체 건수), `RESULT`(`CODE`, `MESSAGE`), `row`(배열)
- 결과 코드 정상: `INFO-000` / `정상 처리되었습니다`

### 3. 필드 (확인됨)
| 필드 | 예시 | 비고 |
|---|---|---|
| STN_CD | 0150 | 4자리 역 코드. 273~274개 역 |
| STN_NM | 서울역(1) | 역명. 괄호 숫자가 노선 번호인 경우가 있다 |
| ELVTR_NM | 승강기)엘리베이터-서울(1)역 섬식(상) 5-1 내부#1 | 설비명. 방면·상하행 텍스트가 섞여 있다 |
| OPR_SEC | B2-B1 | 운행 층 구간 |
| INSTL_PSTN | 시청 방면5-1,남영 방면6-4 | 설치 위치 설명. 방면 텍스트가 들어 있다 |
| USE_YN | 사용가능 / 보수중 | 상태 값. 2종류만 확인됨 |
| ELVTR_SE | EV / ES / WL / MW | 설비 종류. EV=엘리베이터 |

- 필드 7개 모두 문자열이다.
- 설비 고유 ID 필드는 없다(확인됨). 중복 키 (STN_CD, ELVTR_NM)는 2,809건 중 0건이다.

### 4. 설비 종류 (확인됨, 2,809건 기준)
- EV(엘리베이터): 866건, 273개 역
- ES(에스컬레이터): 1,884건
- WL(휠체어리프트): 41건
- MW(무빙워크): 18건
- 엘리베이터 모델에는 EV만 넣는다.

### 5. 상태 표현 (확인됨)
- `USE_YN` 값은 `사용가능`, `보수중` 두 가지뿐이다.
- 실제 응답(2026-11-13 호출 시점): 전체 사용가능 2,680 / 보수중 129. EV 기준 사용가능 845 / 보수중 21.
- `고장`, `점검` 같은 별도 상태 값은 확인되지 않았다.
- 정상 설비도 응답에 포함된다(사용가능 2,680건).
- 보수중 → 가동 안됨, 사용가능 → 가동중으로 매핑한다(DB 값 기준, 결정 사항).

### 6. 갱신 시각 (미확인: 원본 시각 없음)
- 응답 본문에는 갱신 시각 필드가 없다(확인됨).
- HTTP `Date` 헤더만 있다. 이는 서버 응답 시각이지 데이터 갱신 시각이 아니다.
- 데이터 갱신 주기는 "매시"로 알려져 있다(공공데이터 포털 설명, 응답으로는 미검증).
- 로컬 CSV(2026-11-12 작성 파일)와 비교하면 같은 2,809건 중 **100건의 `USE_YN`이 바뀌었다**(사용가능→보수중 85건, 보수중→사용가능 15건). 상태가 시간에 따라 변한다는 뜻이다.
- 결론: `observed_at`은 원본에 없으므로 NULL이다. TTL 기준은 `fetched_at`이다. 2시간 TTL은 매시 갱신 기준의 추정이며 (미검증).

### 7. 역 코드와 역명
- 역 코드 STN_CD는 274개(설비가 있는 역 273개)다. 동묘앞은 `0159`다.
- 같은 역명이 여러 노선에 있는 경우 역명 끝에 `(n)`으로 노선 번호가 붙는다(예: `서울역(1)`, `동묘앞(1)`).
- 괄호가 없는 역명도 많다(예: `종각`, `강동`). 이 경우 노선은 이 API로 확인할 수 없다.

### 8. 호선 범위 (부분 확인, 미검증)
- EV 설비의 역명 괄호 번호는 1~8만 나타났다(9호선 번호 없음).
- 하지만 EV 866건 중 550건은 역명에 괄호 번호가 없어서 노선을 판정할 수 없다.
- 노선 컬럼이 없으므로 1~8호선 범위는 **미검증**이다. 노선 매핑은 T13(역·노선 원본)에서 해야 한다.

### 9. 위치 설명
- `INSTL_PSTN`과 `ELVTR_NM`에 방면과 출입구 정보가 있다(예: `시청 방면5-1`, `4번 출입구`).
- 방면은 상·하행으로 나누지 않고 원문 그대로 저장한다(결정 사항).
- 방면 뒤 번호(예: 5-1)의 의미는 미검증이다.

### 10. 로컬 CSV와의 차이
- 같은 키 2,809개가 모두 일치한다. 차이는 `USE_YN` 100건뿐이다.
- 즉 API는 실시간 상태를 준다. 로컬 CSV는 2026-11-12 시점 스냅샷이다.

### 11. 미확인 항목 (미검증)
- 갱신 주기 "매시"의 실제 동작(응답으로 확인 불가)
- 원본 갱신 시각 필드 존재 여부(응답에 없음)
- 1~8호선 전체 범위와 정상 설비 전부 포함 여부(노선 컬럼 없음)
- 호출 제한(일일 한도)과 응답 시간의 정확한 기준(미측정)
- 역명과 노선의 다대다 관계(역 원본 데이터 T13에서 확인)

## OA-101 열차 시간표 (Issue #15)

> 확인일: 2026-11-13. 서울 열린데이터광장 키(`SEOUL_OPEN_API_KEY`)로 실제 호출했다. 키는 기록하지 않는다.

### 1. 호출 방식 (확인됨)
- 엔드포인트: `http://openapi.seoul.go.kr:8088/{KEY}/json/SearchSTNTimeTableByIDService/{시작}/{끝}/{STATION_CD}/{WEEK_TAG}/{INOUT_TAG}/`
- 서비스명 `SearchSTNTimeTableByIDService`는 호출로 확인했다. 서울 열린데이터광장 상세 페이지(OA-101, "역코드로 지하철 열차 시간표 검색")에는 서비스명과 인자 표가 정적으로 없어서 공식 명세로는 확인하지 못했다.
- 요청 인자 순서: 시작, 끝, 역 코드(`STATION_CD`), 요일(`WEEK_TAG`), 방향(`INOUT_TAG`). 5개 모두 필수다. 4개만 보내면 `ERROR-300`(필수 값 누락)이다.
- 한 번에 최대 1,000건이다. 끝-시작이 1,000을 넘으면 `ERROR-336`이다. 역·요일·방향 한 조합이 약 190~250건이라 1번 호출로 모두 받는다.
- 역 코드는 OA-15994의 `STN_CD`(예: 서울역 `0150`)와 같은 값으로 호출이 성공했다. 3개 역(0150 서울역, 0159 동묘앞, 0222 강남)만 시험했다.

### 2. 응답 (확인됨)
- 최상위 키: `SearchSTNTimeTableByIDService` → `list_total_count`, `RESULT`, `row`.
- 정상 `INFO-000`. 존재하지 않는 역 코드나 `WEEK_TAG=9`는 `INFO-200`(해당하는 데이터가 없습니다)이다. 오류 시 최상위 키는 `RESULT`다.
- 응답 시간: 18회 호출에서 0.19~0.35초(평균 0.25초). 표본이 작다.

### 3. 필드
| 필드 | 예시 | 상태 | 의미 |
|---|---|---|---|
| LINE_NUM | 01호선 | 확인됨 | 호선. 0150·0159는 01호선, 0222는 02호선 |
| FR_CODE | 133 | 확인됨 | 외부 코드(역 코드와 다름). 서울역 133, 동묘앞 127, 강남 222 |
| STATION_CD | 0150 | 확인됨 | 요청한 역 코드와 같다 |
| STATION_NM | 서울역 | 확인됨 | 역명 |
| TRAIN_NO | K1902 | 확인됨 | 열차 번호. 접두어 K(1호선 경부·경인 계열), S, 숫자(2호선). 같은 키 중복 0건 |
| ARRIVETIME | 07:18:00 | 확인됨 | 도착 시각 `HH:MM:SS` |
| LEFTTIME | 05:20:30 | 확인됨 | 출발 시각 `HH:MM:SS` |
| ORIGINSTATION | 1728 | 확인됨 | 시발역 코드. 이 역이 시발이면 요청 역 코드와 같다 |
| DESTSTATION | 0150 | 확인됨 | 종착역 코드 |
| SUBWAYSNAME / SUBWAYENAME | 천안 / 서울역 | 확인됨 | 시발역명 / 종착역명 |
| WEEK_TAG | 1 | 확인됨 | 요일 구분. 1, 2, 3만 데이터가 있다 |
| INOUT_TAG | 1 | 확인됨 | 방향 구분. 1, 2 |
| FL_FLAG | (빈 값) | 확인됨 | 4,085건 모두 빈 문자열. 의미 미검증 |
| DESTSTATION2 | (빈 값) | 확인됨 | 4,085건 모두 빈 문자열. 의미 미검증 |
| EXPRESS_YN | G / D | 부분 확인 | G 3,802건, D 283건. D는 K접두어 열차에서 나타나 급행으로 추정(미검증) |
| BRANCH_LINE | (빈 값) | 확인됨 | 4,085건 모두 빈 문자열. 의미 미검증 |

적재 검증(#71): `EXPRESS_YN`이 G·D가 아니거나, `TRAIN_NO`·`ORIGINSTATION`·`DESTSTATION`이 1~16자 영숫자가 아니거나, `LINE_NUM`이 없거나 1~8호선이 아니거나 연결된 노선과 다르면 적재 전체를 거부한다. 2026-11-14 전체 수집으로 적재된 279,458행의 열차 번호·시발·종착 코드는 모두 이 형식에 맞았다(2026-11-15 확인). 다만 당시 노선 불일치로 건너뛴 행 수와 `EXPRESS_YN` 원본 값 분포는 기록이 없어 확인하지 못했다(미검증).

- 필드 17개 모두 문자열이다.

### 4. 값의 의미
- `WEEK_TAG`: 1=평일, 2=토요일, 3=일요일·공휴일로 추정한다. 1이 평일 건수가 가장 많고(0150 기준 246/242건), 2와 3은 건수가 같다(233/231건). 데이터 차이로 보면 맞지만 공식 표로는 확인하지 못했다(미검증). 2와 3의 내용이 완전히 같은지는 비교하지 않았다.
- `INOUT_TAG`(1호선, 확인됨): 1은 광운대·청량리·양주·의정부 방면(상행), 2는 인천·서동탄·천안·신창 방면(하행)이다. 정차 역 0150·0159에서 방면이 일치했다.
- `INOUT_TAG`(2호선, 미검증): 1과 2 모두 종착역이 성수 계열이다. 내선·외선 중 어느 쪽인지 확인하지 못했다.
- 시각 형식: 시각이 24시를 넘는 값이 있다(예: `24:09:30`, `24:48:00`). 4,085건 중 34건이다. `datetime.time`으로 바로 파싱하면 실패한다. 자정 이후 운행은 시각 문자열 처리가 필요하다.
- 시발역 행: 이 역이 시발이면 `ARRIVETIME`이 `00:00:00`이다(43건, 모두 `ORIGINSTATION`==역 코드). 종착역 행은 `LEFTTIME`이 `00:00:00`이다(44건, `DESTSTATION`==역 코드). `00:00:00`은 "없음" 값이다. 실제 자정이 아니다.
- 정렬: 0150 평일 상행 응답은 `LEFTTIME` 순으로 정렬되어 있다(확인됨). 종착 행 `LEFTTIME=00:00:00`은 정렬에 맞지 않아 보이니 `ARRIVETIME`으로 보완해야 한다.

### 5. 시간표 기준 (공식 설명 확인)
- 서울 열린데이터광장 데이터셋 설명: 시간표 기반이며 실제 도착 시각과 다를 수 있다. 서울교통공사 1~9호선(2020-06-17부터).
- 따라서 이 데이터는 계획 시각이다. 지연은 반영되지 않는다.

### 5-1. 인접역 추출에 쓰는 방식 (2026-11-14 결정)
- 같은 `TRAIN_NO`가 정차하는 역을 시각 순으로 정렬해 이웃한 두 역을 인접역으로 본다(`app/services/edge_derive.py`). 시각이 없는 쪽(시발의 도착, 종착의 출발)은 있는 쪽을 쓴다.
- `EXPRESS_YN=D`(급행 추정)는 제외하고, 서로 다른 열차 2대 이상이 확인한 쌍만 인정하며, 두 역 사이 시간 차가 20분을 넘으면 제외한다.
- 이 방식은 공식 인접역 자료가 아니다. 1호선 분기(병점·인천 방면 등)와 2호선 지선은 열차별 정차 순서로 처리되며 실제 데이터로 검증하지 않았다(미검증).
- 이슈 #16의 간선 출처 결정은 "OA-101 연속 역 추출"로 한다. OA-22724는 비교용이며 호출하지 않았다.

### 6. 미검증 (OA-101)
- 공식 인자 표(`WEEK_TAG`, `INOUT_TAG` 값 정의)
- 2호선 `INOUT_TAG`의 내선·외선 매핑
- `EXPRESS_YN`의 D 의미, `FL_FLAG`·`DESTSTATION2`·`BRANCH_LINE`의 의미(전부 빈 값)
- 2·3호선 이외 노선(3~8호선)의 응답과 분기 노선(1호선 병점·인천 방면, 2호선 지선 등) 처리
- `WEEK_TAG=2`와 `3`이 같은 시간표인지, 공휴일 처리
- 일일 호출 한도(미측정), 3개 역 외의 전체 역 호출 가능 여부
- `STATION_CD` 형식이 모든 역에서 OA-15994 `STN_CD`와 같은지

## OA-22724 최단경로 이동정보 (Issue #15)

> 상태: **실제 호출 검증 못 함(미검증).** 공공데이터포털 인증키가 없어서 응답을 확인하지 못했다.

### 1. 확인된 것 (공개 명세 조회)
- 이 API는 서울 열린데이터광장 `openapi.seoul.go.kr:8088` 방식이 아니라 공공데이터포털(`data.go.kr` 15143842, "서울교통공사_최단경로이동정보")의 REST API로 안내된다. 서울 열린데이터광장 OA-22724 페이지는 개요만 있고 "서비스 종료 안내"와 "URL 오류 안내" 문구가 보인다. 템플릿 문구인지 실제 상태인지는 구분하지 못했다(미검증).
- 기준 URL: `https://apis.data.go.kr/B553766/path2` (data.go.kr 메타데이터)
- 요청 인자(data.go.kr 상세 페이지 기준, 호출 미검증):

| 인자 | 필수 | 설명 |
|---|---|---|
| serviceKey | 필수 | 공공데이터포털 인증키 |
| dataType | 선택 | JSON / XML(기본 XML) |
| dptreStn | 필수 | 출발역 |
| arvlStn | 필수 | 도착역 |
| searchDt | 필수 | `yyyy-MM-dd hh:mm:ss` |
| searchType | 선택 | duration(기본, 최소 시간) / distance / transfer |
| exclTrfstns | 선택 | 환승 제외역, 쉼표 구분 |
| thrghStns | 선택 | 경유역, 쉼표 구분 |
| schInclYn | 선택 | 시간표 포함 여부, N이면 경로만(기본 Y) |

- 응답은 `header`와 `body` 두 키만 문서화되어 있다. 세부 필드는 문서에 없다. 최소 시간·최단 거리·최소 환승 3종 경로와 구간별 정차역·소요 시간·거리·환승 여부를 준다고 설명한다.

### 2. 실제 호출 결과
- 키 없이 `https://apis.data.go.kr/B553766/path2` 와 `/path2/{추측한 오퍼레이션명}`을 호출하면 모두 `NO_OPENAPI_SERVICE_ERROR`(코드 12, 서비스 없음)가 나온다. 기본 경로와 오퍼레이션명 6개(getShortestRoute 등 추측)가 모두 같다. 정확한 오퍼레이션명은 **확인하지 못했다.**
- 이전 세션의 서울 열린데이터광장 방식 호출은 일부에서 `ERROR-500`이었다. 이 API가 서울 키로 호출되는 서비스가 아닐 가능성이 높다(미검증).

## 역 코드 매핑 검증 (Issue #16)

> 확인 기준: 로컬 `dev.db`(2026-11-14 적재본)와 `data/seed/`를 읽기 전용으로 대조했다. 코드·데이터는 바꾸지 않았다.

### 1. 시간표 역 276개와 시드 역 240개는 단위가 다를 뿐 불일치가 아니다
- **276 = 역-노선 쌍(`station_lines`)**, OA-12035 역번호(4자리 패딩) 1개당 1개다. **240 = 고유 역(`stations`)**이다.
- 차이 36은 환승역 병합이다. 34개 역이 2개 이상 노선을 갖는다(2개 노선 32역, 3개 노선 2역: 종로3가 1·3·5호선, 동대문역사문화공원 2·4·5호선). 276 − 36 = 240이다.
- 34개 환승 그룹은 모두 `station_review.csv`에서 `TRANSFER_CANDIDATE / CONFIRMED`이고 근거는 `transfer_evidence_oa13290.csv`(OA-13290 공식 환승 기록)다. 역명만으로 합치지 않았다.
- 같은 역명인데 서로 다른 `station_id`인 경우는 없다(0건).
- 시간표는 276개 역-노선 쌍 전부에 행이 있다(확인). 노선별 쌍 수(1호선 10, 2호선 50, 3호선 34, 4호선 26, 5호선 56, 6호선 39, 7호선 42, 8호선 19)가 시드와 같다.

### 2. 외부 코드와 역의 대응
- OA-12035 역번호 → 역-노선 쌍은 276건 모두 1:1이다(`uq_station_external_ids_source_code`).
- OA-15994 `STN_CD` 대응은 274건이다(`external_code_links.csv`). 근거는 `STN_CD == OA-12035 역번호(4자리 패딩)`이고 이름 매칭이 아니다.
- **OA-15994 대응이 없는 OA-12035 코드 2건(REVIEW)**: `0321` 충무로(3호선), `2538` 청구(5호선). OA-15994 쪽에 이 코드가 없는 이유는 확인하지 못했다(미검증). 임의로 연결하지 않았다.
- OA-15994 코드가 OA-12035에 없는 경우는 없다(0건). 적재된 엘리베이터 중 코드 미매핑은 0건이다.

### 3. 이름 표기 차이 (코드는 1:1, 이름만 다름)
`station_review.csv`의 `NAME_VARIANT` 71건이다. 코드로 대응했고 이름으로 합치지 않았다.
- `ACCEPTED_BY_CODE` 66건: 괄호 부연 등이 붙은 표기 차이(예: 청량리 / 청량리(서울시립대입구))다.
- `PENDING` 5건(확정하지 않음, REVIEW): `0150`·`0426` 서울역(OA-15994 `서울역(n)` / 시드 `서울`), `2629` 삼각지(OA-15994 `삼각지(전쟁기념관)(6)`), `2730` 자양(OA-15994 `자양(뚝섬한강공원)`), `2810` 암사역사공원(시드는 `역` 접미). 이 5건의 노선 일치 여부는 미검증이다. 단, `0150`·`0426`은 환승 그룹으로는 확정되어 있다.

### 4. 간선 출처 결정 (OA-101 정차 순서 추출, D16)
인접 간선 출처는 **OA-101 시간표에서 같은 열차의 정차 순서로 추출**한다(OA-22724 비교용 호출은 하지 않았다). 공식 인접역 자료가 없고(OA-22724는 키 발급이 필요하고 명세만 확인), 시간표가 모든 노선과 분기·지선의 열차별 정차 순서를 담고 있어 한 방식으로 처리할 수 있기 때문이다. 현재 적재량은 `ADJACENT 269`(source OA-101)와 `TRANSFER 38`(source OA-13290)이다. 급행 추정(`EXPRESS_YN=D`)과 지지 열차가 상대적으로 적은 간선(최다 지지 대비 20% 미만)은 제외한다. 한계: 공식 자료가 아니므로 간선 전체를 공식 인접역과 대조하지 못했다(미검증). 5호선 분기와 2호선 지선은 확인했고, 6호선 응암순환은 단방향이라 방향 판별이 없다.
